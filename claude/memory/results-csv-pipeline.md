**The two living results tables** (user directive 2026-07-08: update on every change).

## How to update (MANDATORY after any campaign, either track)
1. Add the new wandb group(s) to `scripts/results_map.py` (csv='summary'|'bridge'|'exclude'+reason).
2. `.venv/bin/python scripts/compile_results_csvs.py --refresh` (refetches the wandb dump;
   per-run @500k histories are cached in analysis/results_cache/hist/, so only new runs fetch).
3. Check `results/compile_audit.txt` — UNMAPPED groups = exit 1; partials listed per group.

## Protocol
Uniform per-run success at the 500k eval point (history-extracted for 1M+ runs); runs dead
before 490k dropped as partial; mean ± 1.96·sd/√n. jax metric evaluation/overall_success;
torch = mean of per-task eval/reward/*/success (== success/overall, verified exact).

## Learning-curve columns (added 2026-07-09, commit 8008370)
Both CSVs also carry `mean_{100,200,300,400}k` / `n_*k` / `per_seed_*k`, always history-sourced
(the summary only holds the last eval), and collected even for runs dropped as partial @500k.
`--refresh-hist` drops `analysis/results_cache/hist/` — REQUIRED for a still-training run, whose
per-run history file is otherwise frozen at first fetch.

## Gotcha: results_map keys on the WANDB GROUP
Relaunching a fixed version of a cell into the same `run_group` silently averages the buggy and
corrected seeds. Give the corrected cell a new group (e.g. `...-RewReg-Shift-Fix`) and mark the
old one `csv=E` with the reason. Bit me on the E3 re-run ([[e3-sf-rewreg-campaign-20260709]]).
GOTCHAS baked in: wandb scan_history is ~500× slower AND returns 0 rows for these key combos
— use history(keys=[metric], samples=2000) with `_step`; resumed runs (fb_state_plain 1M→1.5M)
have NO 500k point in history → correctly dropped (plain-FB cube @500k comes from FB-State-Flow).
